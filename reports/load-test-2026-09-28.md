# EduNex Load Test Report - 2026-09-28

## Scope

- Target: local backend at `http://127.0.0.1:3102`
- Runtime: one local Node.js process with `SERVE_FRONTEND=false` and background jobs disabled
- Database: configured MongoDB connection from the backend environment
- Tool: k6 via `edunex-b/scripts/run-k6-common-api-steps.mjs`
- Steps requested: 10, 100, 1,000, and 10,000 requests
- VU scaling used by script: 1 VU, 10 VUs, 100 VUs, and 250 VUs respectively
- Endpoints tested: `GET /api/health/db`, `GET /api/categories`, `GET /api/courses`
- Thresholds: failed requests < 1%, checks > 99%, p95 < 1,500 ms, p99 < 3,000 ms

Note: these steps model increasing request volume, not exact logged-in user concurrency. Authenticated login, OTP, payment, subscription, and write-heavy flows were not included in this read-only run.

## Executive Summary

The backend stayed available through all tested steps. Every tested endpoint returned 0.00% failed requests and 100.00% check pass rate, including the 10,000 request runs.

Normal read endpoints performed well at 10, 100, and 1,000 request steps. `GET /api/categories` remained healthy at 10,000 requests. `GET /api/courses` also had no request failures at 10,000 requests, but crossed the p99 latency threshold due to tail spikes. `GET /api/health/db` crossed the latency threshold at 10,000 requests because each request performs a database health check.

## Findings

- Availability is strong for this read-only local test: all 31,110 real k6 requests completed successfully with 0.00% failed requests.
- `GET /api/categories` is the cleanest endpoint under this profile, passing all four steps including 10,000 requests.
- `GET /api/courses` has a tail-latency issue at 10,000 requests. The low p95 with high p99 suggests a small subset of requests are stalling rather than the entire endpoint being slow.
- `GET /api/health/db` should not be treated as a normal user-facing capacity endpoint. It intentionally touches database health, and the 10,000 request step amplified that dependency.

## Recommendations

1. Run the same 10/100/1,000/10,000 ladder against staging or production-like infrastructure before making real capacity claims.
2. Profile `GET /api/courses` at 10,000 requests to identify the p99 stall source: database query plan, payload size, connection pool pressure, or Node event loop blocking.
3. Add a lighter liveness endpoint for load balancers and uptime checks, and keep DB health checks on a separate readiness endpoint with lower probe frequency.
4. Add authenticated load coverage for mobile login, course access checks, AI tutor, and payment-adjacent read flows.
5. Repeat with realistic mixed traffic instead of isolated endpoints: browse courses, fetch categories, load course detail, authenticate, and access owned content.
